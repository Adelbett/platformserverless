Le backend ne gère ni mot de passe ni session : configuré en mode \texttt{STATELESS}, il agit comme serveur de ressources OAuth2 et se contente de valider les jetons émis par Keycloak. Un filtre de synchronisation crée l'utilisateur local à sa première requête, ce qui rattache l'identité Keycloak au modèle de rôles de la plateforme.

\subsubsection{Configuration CORS}

Le navigateur autorise par défaut une page à appeler uniquement son propre domaine. Sans configuration CORS explicite, le portail ne pourrait pas contacter l'API ; avec une configuration trop permissive, n'importe quel site pourrait le faire à la place de l'utilisateur.

Le backend restreint donc les origines autorisées à une liste explicite, portée par la propriété \texttt{app.cors.allowed-origins}, plutôt qu'un caractère générique. Cette configuration n'autorise l'envoi des identifiants de session (\texttt{allowCredentials}) que pour les origines listées, et limite les méthodes HTTP acceptées à celles réellement utilisées par l'API (\texttt{GET}, \texttt{POST}, \texttt{PUT}, \texttt{PATCH}, \texttt{DELETE}, \texttt{OPTIONS}).

Les permissions accordées individuellement à un membre couvrent le déploiement et la suppression d'applications, la gestion des sujets Kafka et de l'\textit{Eventing}, la consultation des journaux et du monitoring, ainsi que la consultation et l'export de la facturation.

\subsubsection{Revue des accès directs par identifiant}

L'authentification et la vérification de permission ne suffisent pas à elles seules : un client authentifié, disposant du droit de supprimer une application, pourrait tenter d'agir sur celle d'un autre client en manipulant l'identifiant transmis dans l'URL. C'est le troisième étage de contrôle représenté sur la figure~\ref{fig:workflow-securite}.

La revue des points d'accès manipulant une ressource par identifiant (journaux de déploiement, moyens de paiement enregistrés) a permis de vérifier, ou le cas échéant de corriger, que chaque accès est bien filtré par l'identité effective de l'appelant, résolue par \texttt{UserContextService}, plutôt que par le seul identifiant transmis dans l'URL. Pour un membre d'équipe, cette identité effective est celle de son CLIENT\_ADMIN, ce qui lui donne accès aux ressources de son équipe sans lui ouvrir celles des autres locataires.

\subsection{Sécurisation de l'infrastructure}

Cilium n'est pas un mécanisme d'authentification : c'est le plugin réseau (CNI) du cluster, chargé d'appliquer les règles \texttt{NetworkPolicy}. La politique retenue est de type \textit{default-deny} : tout trafic non explicitement autorisé est refusé, en entrée comme en sortie. Seuls sont ouverts les flux nécessaires au fonctionnement de la plateforme — passerelle d'entrée, plan de contrôle Knative, supervision, résolution DNS et bus Kafka partagé. Le trafic direct entre deux namespaces de locataires reste refusé.

Une limite doit être signalée : cette création automatique ayant été introduite en cours de projet, les namespaces créés antérieurement ne portent pas la politique, faute de reprise rétroactive.

\subsection{Conclusion}

Au terme de ce sprint, les mesures de durcissement identifiées au fil du projet sont consolidées et présentées comme une chaîne cohérente : authentification par jeton, autorisation par rôle et permission, vérification de propriété des ressources, restriction des origines autorisées, et isolation réseau des locataires. Les risques résiduels sont documentés plutôt que passés sous silence.

\subsection{Implémentation de la pipeline}

Le pipeline est décrit en syntaxe déclarative dans le fichier \textit{Jenkinsfile} versionné avec le code source. L'extrait~\ref{lst:jenkinsfile} en présente les parties essentielles.

\begin{lstlisting}[style=yamlstyle, language={}, basicstyle=\ttfamily\scriptsize,
  caption={Extrait du \textit{Jenkinsfile} du pipeline \texttt{platform-backend}},
  label={lst:jenkinsfile}]
pipeline {
    agent any
    options { retry(2) }            // relance le pipeline sur echec transitoire
    tools   { maven 'maven-3'; jdk 'jdk-21' }

    environment {
        IMAGE_NAME = 'adelbettaieb/platform-api'
        IMAGE_TAG  = "v${BUILD_NUMBER}"
        NAMESPACE  = 'platform'
    }

    stages {
        stage('Checkout') {
            steps {
                retry(3) {          // fiabilisation du clone Git
                    git branch: 'main',
                        credentialsId: 'github-credentials',
                        url: 'https://github.com/Adelbett/platformserverless.git'
                }
            }
        }

        stage('Build JAR') {
            steps {
                dir('backend-api') { sh 'mvn clean package -DskipTests' }
            }
        }

        stage('Docker Build & Push + Deploy') {
            steps {
                withCredentials([usernamePassword(
                    credentialsId: 'dockerhub-credentials',
                    usernameVariable: 'DOCKER_USER',
                    passwordVariable: 'DOCKER_PASS')]) {

                    sh "/kaniko/executor \
                        --context=dir://$(pwd)/backend-api \
                        --dockerfile=$(pwd)/ci-cd/docker/backend-kaniko.Dockerfile \
                        --destination=${IMAGE_NAME}:${IMAGE_TAG} \
                        --destination=${IMAGE_NAME}:latest \
                        --use-new-run --snapshot-mode=redo"

                    sh "kubectl set image deployment/platform-api \
                        platform-api=${IMAGE_NAME}:${IMAGE_TAG} -n ${NAMESPACE}"
                    sh "kubectl rollout status deployment/platform-api -n ${NAMESPACE}"
                }
            }
        }
    }
}
\end{lstlisting}

Quelques éléments méritent d'être soulignés dans cet extrait.

Le bloc \texttt{retry} apparaît à deux niveaux : sur le pipeline entier et sur l'étape de clone Git, la plus sujette aux échecs transitoires. Les identifiants, qu'il s'agisse de GitHub ou de Docker Hub, ne figurent jamais en clair : ils sont injectés depuis le magasin de \textit{credentials} de Jenkins.

L'image est construite par \textbf{Kaniko}, qui produit une image de conteneur depuis l'intérieur d'un pod, sans démon Docker ni privilège root — une exigence pour construire à l'intérieur d'un cluster Kubernetes. Elle est publiée sous deux étiquettes : une version immuable \texttt{v\$\{BUILD\_NUMBER\}} et \texttt{latest}.

Le déploiement utilise l'étiquette versionnée, et non \texttt{latest} : Kubernetes ne détecterait aucun changement si le nom de l'image restait identique, et aucun \textit{rollout} ne serait déclenché. La commande \texttt{kubectl rollout status} clôt le pipeline en vérifiant que les nouveaux pods deviennent réellement disponibles ; le build échoue dans le cas contraire.

\section{Conclusion}

La Release 3 a consolidé la solidité technique de la plateforme sans lui ajouter de nouvelle fonctionnalité visible : durcissement de la sécurité par la restriction du RBAC, de la configuration CORS et des accès par identifiant, puis industrialisation des chaînes de déploiement continu des quatre composants du projet. Ce travail d'industrialisation, présenté ici avec la même rigueur que les fonctionnalités abouties, n'a été que partiellement mené à son terme : ce constat est assumé et repris dans les perspectives de la conclusion générale.
