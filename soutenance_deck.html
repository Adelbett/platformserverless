Complexité de configuration

Chaque déploiement exige plusieurs manifestes YAML (Deployment, Service, Ingress, RBAC, Secrets).

Event-driven manuel

Aucune isolation entre équipes, ni quotas, ni contrôle d'accès par développeur.

03 / 20
Cadre général — étude de l'existant

Pourquoi pas Vercel, Heroku ou EKS managé ?

Vercel

Scale-to-zero natif, mais limité au frontend JavaScript. Pas de Kafka, pas de multi-tenancy, pas d'on-premise.

Heroku

Déploiement Git + image Docker simple. Pas de scale-to-zero, pas de Kafka natif, coûteux à l'échelle.

Amazon EKS

Kubernetes managé puissant mais brut : multi-tenancy et event-driven restent entièrement manuels, expertise avancée requise.

Aucune de ces solutions ne réunit scale-to-zero, event-driven natif et multi-tenancy on-premise dans un seul produit — c'est l'espace que PlatformServerless occupe.

06 / 20
Réalisation — infrastructure réseau

Comment un tenant reste isolé d'un autre

  • MetalLB — attribue une IP externe de type LoadBalancer (bare-metal, pas de cloud provider).
  • Kourier — passerelle HTTP/HTTPS d'entrée pour tous les Knative Services.
  • Cilium — CNI du cluster, applique les NetworkPolicy qui isolent chaque tenant.
  • Chaque client obtient un namespace user-<client> créé à sa première utilisation, avec sa NetworkPolicy générée automatiquement.

Réalisation — le backend comme cerveau

Fabric8 et Kafka AdminClient : deux bibliothèques, deux rôles

Fabric8 Kubernetes Client

Bibliothèque Java exécutée dans le process du backend. Crée / lit / modifie les ressources Kubernetes et les CRD Knative (Service, Revision, KafkaSource, Trigger).

Kafka AdminClient

Bibliothèque Java dédiée à Kafka. Crée / supprime les topics eux-mêmes — une opération d'administration Kafka, indépendante de Kubernetes.

// EventingService.java — deux clients distincts, même process private void createKnativeKafkaSource(...) { // Fabric8 → CRD KafkaSource kubernetesClient.genericKubernetesResources("sources.knative.dev/v1beta1", "KafkaSource")... } // KafkaService.java adminClient.createTopics(...); // Kafka AdminClient → topic Kafka réel

Réalisation — sécurité applicative

Keycloak, JWT, et une permission par endpoint

Keycloakauthentifie, émet le JWT
↓
Spring Security (oauth2-resource-server)valide le JWT contre l'issuer Keycloak
↓
Rôle → Permission → @PreAuthorizeADMIN · CLIENT_ADMIN · DEVELOPER
@PreAuthorize("@permissionService.has(authentication.name, 'MANAGE_EVENTING')") public ResponseEntity<Void> createTrigger(...)
La vérification de permission se fait avant d'entrer dans le contrôleur — un rôle DEVELOPER ne peut jamais atteindre un endpoint réservé à MANAGE_EVENTING.

Validation — limites

Une limite réelle, testée cette semaine

Knative Serving ne route que du HTTP/HTTP2/gRPC — un PostgreSQL déployé comme Knative Service est injoignable en TCP brut.

  • Testé avec un vrai microservice Spring Boot (order-service).
  • Résultat : CrashLoopBackOff au démarrage.
  • Perspective : les ressources stateful nécessitent un StatefulSet Kubernetes classique, hors du moteur serverless.
org.postgresql.util.PSQLException: Connection to order-db:5432 refused. Caused by: java.net.ConnectException: Connection refused

Conclusion — perspectives

Ce qui suit une fois la limite posée

Ressources stateful

Introduire un second type de déploiement (StatefulSet) à côté des apps serverless.

BD managée par tenant

Provisionner une base par client hors du moteur Knative, credentials fournis au client.

Sécurité M2M

Étendre le contrôle d'accès machine-à-machine au-delà du webhook Stripe.
